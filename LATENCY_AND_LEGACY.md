# Addressing Latency and Legacy-System Objections

The multi-vault architecture creates a real engineering objection that should not be minimized: if identity, substantive content, relationship-mapping information, authorization state, cryptographic/reconstruction material, provenance, and output authority are placed behind independent controls, a naive implementation can create multiple serial network round trips, repeated policy evaluation, repeated attestation, and expensive reconstruction on every AI interaction. That would be unsuitable for latency-sensitive enterprise AI. The architecture therefore must not be implemented as "call every vault sequentially for every token." Its security invariant is separation of authority, not unnecessary serialization.

The reference implementation uses four practical latency principles.

1. **Cold-path preparation.** Stable or bounded-validity material such as compiled policy predicates, permitted-association graphs, protected identity indices, workload measurements, destination manifests, attestation collateral, revocation snapshots, provenance schemas, and migration metadata can be prepared before the consequential request. Precomputation does not itself authorize reconstruction or release; current session, epoch, scope, revocation, provenance, association, receipt, and boundary predicates remain load-bearing on the hot path.

2. **Parallel independent vault-local release.** Identity, content, and relationship vaults do not have to be contacted serially. Once a valid Reconstruction Authorization Object has been formed, independent vault-local decisions can be fanned out concurrently. The slowest required protected domain, rather than the sum of all independent vault latencies, can dominate that stage. The included `VaultCoordinator` supports parallel fan-out. This does not weaken the rule that denial or unverifiable state from any required vault aborts reconstruction.

3. **Minimum-necessary reconstruction.** The Protected Reconstruction Domain does not rebuild a durable enterprise-wide joined record. It resolves only the fields and associations permitted for the particular protected session and produces an ephemeral minimum-necessary view. This reduces data transfer, decryption, parsing, model-context size, and subsequent verification work compared with repeatedly materializing a complete joined record.

4. **Small output-finality hot path.** Expensive preparation can occur before or during processing, but the final release path need only verify the current load-bearing state: session/epoch, exact output binding, destination/recipient, association/provenance scope, receipt commitment, capability binding, and Output Release Boundary. No optimization is valid if it allows a Candidate Output to become externally usable without these current checks.

The supplied benchmark is deliberately narrow. On the reference environment, 500 warm, local, single-process iterations with three **sequential local** vault calls produced the following illustrative measurements: RAO issue median 112.40 microseconds; three vault-local releases median 622.19 microseconds; protected reconstruction median 521.33 microseconds; seal + POVR commitment + capability + boundary release median 1085.32 microseconds; and the complete protected path median 2378.18 microseconds. These values are not protocol guarantees. They exclude AI inference, network/RPC latency, remote vaults, remote attestation, HSM/KMS access, distributed consensus or commit, human approval, production logging, storage contention, and geographically distributed deployment. Parallel fan-out exists in the code, but a local CPU benchmark cannot establish the latency benefit of parallel remote vault RPCs.

## Legacy-System Deployment

The architecture does not require an enterprise to replace every existing database, AI model, application, API, or message system at once. A mandatory mediation layer can be inserted as a database proxy, data-access gateway, service-mesh sidecar, API gateway, retrieval proxy, model-serving wrapper, output adapter, database-commit interceptor, file-system filter, or network-egress controller. The legacy application can continue using a familiar interface while the mediation layer converts requests into bounded reconstruction requests, protected component requests, authorization references, provenance-labelled values, sealed Candidate Outputs, and output-release operations.

Legacy data migration can also be incremental. A complete existing record can initially remain in a legacy store while the protected layer begins separating new records, removing sensitive mappings first, tokenizing identity fields, moving relationship information into an independently controlled relationship-mapping domain, and preventing unrestricted joins through a mandatory gateway. Existing records can be decomposed when first accessed. A legacy database may temporarily serve as an identity source, content source, relationship source, or untrusted input, but migration status must resolve conservatively: an ambiguous or partially migrated record must not receive broader authority merely because migration is incomplete.

A legacy AI workload likewise need not understand the entire multi-vault protocol. It may receive only the ephemeral reconstructed view through an ordinary structured interface while provenance is maintained in a parallel protected control plane and its generated output is captured before external release. Where the workload cannot itself provide useful attestation, a measurable enclosing runtime, container, virtual machine, sidecar, or reference-monitor boundary can be used only if that enclosing boundary actually prevents escape around the protected data and output paths.

The non-negotiable requirement is **mandatory mediation**. A proxy or sidecar that can be bypassed by an old database credential, direct model endpoint, debug interface, alternate API, cached credential, unmanaged retrieval path, file output, message channel, or network route does not establish Technical Non-Joinability or Technical Non-Completability. Compatibility is useful only where the legacy bypass path is removed, disabled, confined, or made technically insufficient to reconstruct protected relationships or release an unverified output.
